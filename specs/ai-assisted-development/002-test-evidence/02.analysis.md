# Test Evidence in Specs-Driven Development - Analysis

## Current State

The Specs-Driven Development guide already requires validation and evidence. The context guide also tells agents to preserve useful execution details. The missing part is an explicit connection between the plan, automated test layers and evidence in execution records.

## Findings

- Unit tests are useful when logic can be isolated.
- Integration tests are useful when persistence, HTTP, messaging or framework behavior matters.
- End-to-end tests are useful for high-value user or consumer journeys.
- Evidence should be representative rather than exhaustive; specs should not become raw CI logs.
- Documentation tasks may validate through builds, link checks, previews or targeted review instead of automated tests.

## Risks

- Over-prescribing tests for every task could create noise.
- Copying full test logs would make specs hard to read.
- Teams may need project-specific validation commands.

## Proposed Approach

Update the guidance to ask for relevant test layers in plans and a concise sample of output in execution and summary artifacts.

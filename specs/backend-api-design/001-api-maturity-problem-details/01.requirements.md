# API Maturity and Problem Details Guidance - Requirements

## Objective

Prepare a documentation update for Flowsy DevGuide based on current official sources and well-established community references about HTTP API design maturity and standardized error responses.

The expected outcome is an actionable guide that helps open source projects and Flowsy-based solutions design HTTP APIs that reach a minimum useful maturity level and use Problem Details consistently for error responses.

## Problem or Need

Flowsy DevGuide documents backend architecture, C# Minimal APIs, Vertical Slice Architecture, data access, mediation and repository conventions, but it does not yet define a focused API guidance baseline for:

- Applying an API maturity model in a pragmatic way.
- Avoiding RPC-style HTTP endpoints when resource-oriented contracts are more appropriate.
- Choosing HTTP methods, status codes, headers and response semantics consistently.
- Returning standardized machine-readable error responses.
- Designing validation, domain and infrastructure errors without leaking implementation details.
- Aligning future Flowsy libraries, templates and tools with a shared API contract style.

Without this guidance, projects can implement compatible backend architecture internally while exposing externally inconsistent APIs. The documentation should reduce that risk with a researched, source-backed baseline.

## Scope

The spec shall prepare research, analysis and planning for updating public DevGuide content related to HTTP API design.

Initial scope includes:

- Research the Richardson Maturity Model as a teaching model for HTTP API evolution.
- Identify the minimum maturity level that Flowsy DevGuide should recommend for most APIs.
- Clarify that the Richardson Maturity Model is not itself a formal standard and must be validated against HTTP and REST sources.
- Research current HTTP semantics for methods, safety, idempotency, status codes, content negotiation, headers and caching.
- Research RFC 9457, `Problem Details for HTTP APIs`, as the current standard that obsoletes RFC 7807.
- Define guidance for `application/problem+json` responses, problem type URIs, extension members, validation errors, localization, correlation, observability and security considerations.
- Evaluate how guidance should affect C# Minimal API examples, Vertical Slice Architecture examples, endpoint conventions, contracts and AI agent context guides.
- Identify whether reusable Flowsy packages, templates or tools should later provide helpers, conventions or examples for this guidance.
- Register the visible documentation change in `CHANGELOG.md` when final guide content is implemented.

## Expected Research Sources

The later analysis shall prioritize primary and current sources:

- IETF RFC 9457, `Problem Details for HTTP APIs`: https://www.rfc-editor.org/rfc/rfc9457
- IETF RFC 9110, `HTTP Semantics`: https://www.rfc-editor.org/rfc/rfc9110
- Roy Fielding's REST architectural style dissertation chapter: https://ics.uci.edu/~fielding/pubs/dissertation/rest_arch_style
- Martin Fowler's explanation of the Richardson Maturity Model: https://martinfowler.com/articles/richardsonMaturityModel.html
- Current official ASP.NET Core documentation for error handling, Problem Details, Minimal APIs and HTTP results.
- Current official OpenAPI documentation when documenting error contracts or API descriptions.

Community articles may be used only as supporting context when they do not contradict official sources.

## Research Questions

The analysis shall answer at least:

- What minimum maturity level should be recommended for APIs built with Flowsy guidance?
- Which parts of Richardson Level 1 and Level 2 are essential for a practical baseline?
- When should Level 3 hypermedia controls be recommended, optional or explicitly deferred?
- How should the guide explain REST constraints without claiming that all HTTP APIs are fully RESTful?
- How should resource names, collection endpoints, command endpoints and long-running operations be modeled?
- How should APIs choose between `GET`, `POST`, `PUT`, `PATCH`, `DELETE` and other methods?
- How should APIs map common outcomes to status codes such as `200`, `201`, `202`, `204`, `400`, `401`, `403`, `404`, `409`, `422` and `500`?
- What should be the default structure for `application/problem+json` responses?
- How should problem `type`, `title`, `status`, `detail` and `instance` be used?
- How should validation errors be represented without inventing an incompatible envelope?
- Which extension members are useful for trace IDs, error codes, validation members or support references?
- What information must be excluded from error responses for security and privacy?
- How should API examples fit C# Minimal APIs, Vertical Slice Architecture and Flowsy package naming conventions?
- What changes are needed in AI-assisted development context guides so agents ask for the right sources and validation evidence?

## Candidate Documentation Impact

The implementation plan shall decide whether to:

- Create a new backend/API design page under `technologies/backend/`.
- Add API sections to existing C# Minimal API and Vertical Slice Architecture pages.
- Add a convention page for HTTP API contracts under `conventions/`.
- Update AI agent context guides so API-related work starts from official HTTP and Problem Details references.
- Add examples that use general open source domain language, such as packages, orders, accounts, projects or releases.

## Acceptance Criteria

- A later analysis inventories the current backend, C# and AI-assisted development pages that mention APIs, endpoints, errors or validation.
- Research distinguishes official standards, official platform documentation and community teaching models.
- The proposal identifies a minimum API maturity baseline suitable for most Flowsy-guided projects.
- The proposal explains how to use RFC 9457 Problem Details without relying on obsolete RFC 7807 guidance.
- The proposal includes examples appropriate for a general community and open source audience.
- The proposal identifies any updates needed for Flowsy libraries, templates or tools as future work rather than implementing them prematurely.
- The implementation plan separates research, structure design, writing, navigation review and `npm run docs:build` validation.

## Out of Scope for This Initial Spec

- Implementing the final public DevGuide pages.
- Creating or changing .NET packages, templates or CLI tools.
- Enforcing API conventions in existing downstream projects.
- Defining a complete REST certification or scoring process.
- Publishing guidance based only on memory or non-official secondary sources.

## Notes for Later Analysis

The analysis should be careful with terminology. The guide can use the Richardson Maturity Model as a learning scaffold, but it should not present the model as a formal standard or as proof that an API is REST-compliant.

> [!warning] Important
> This requirements draft only prepares research and planning. Do not publish the final guide update without a reviewed analysis and approved implementation plan.

# Analysis - API Maturity and Problem Details Guidance

## Current State

Flowsy DevGuide already has several places where HTTP API guidance can land:

- `technologies/backend/concepts.md` defines general backend API contract, validation, error structure and traceability guidance.
- `technologies/backend/vertical-slice-architecture/concepts.md` explains that slices can include Minimal API endpoints, commands, queries, validators, state and tests.
- `technologies/backend/vertical-slice-architecture/csharp-minimal-apis.md` contains concrete endpoint examples.
- `technologies/backend/dotnet/csharp.md` covers request/response DTOs and Minimal API endpoint naming.
- `ai-assisted-development/context-guides/backend-vsa-minimal-api.md` tells agents to keep HTTP contracts explicit and stable, and to validate boundary input.
- `technologies/testing/` already covers integration tests for HTTP behavior and evidence reporting.

The guide has the right structure for API guidance, but the current content only says that errors should be consistent and that contracts should be stable. It does not yet define an API maturity baseline, a status-code decision model, or an RFC 9457 Problem Details convention.

## Source Findings

### Problem Details

RFC 9457 is the current IETF Standards Track document for `Problem Details for HTTP APIs`. It was published in July 2023 and obsoletes RFC 7807. It defines a common JSON model for machine-readable HTTP API errors and the `application/problem+json` media type.

Important points for the guide:

- Problem Details are intended to avoid inventing new error formats for HTTP APIs.
- They fit most naturally with `4xx` and `5xx` responses.
- The core members are `type`, `status`, `title`, `detail` and `instance`.
- `type` is the primary problem identifier; absolute and resolvable URIs are encouraged when possible.
- `status`, when present, must match the actual HTTP status code generated by the origin server.
- `title` describes the problem type and should not vary per occurrence except for localization.
- `detail` should help the client correct the problem and should not be parsed by clients.
- Extension members are allowed and are the right place for structured data such as validation errors.
- Security considerations are central: Problem Details should not expose implementation internals or attack vectors.

Source: https://www.rfc-editor.org/rfc/rfc9457

### HTTP Semantics

RFC 9110 is the current core reference for HTTP semantics. API maturity guidance should rely on this source for methods, status codes, content negotiation, headers, representations, caching, safety and idempotency.

The guide should not define HTTP method behavior from preference or framework habits. It should map endpoint recommendations to the HTTP semantics in RFC 9110 and then show pragmatic examples for common application cases.

Source: https://www.rfc-editor.org/rfc/rfc9110

### Richardson Maturity Model

Martin Fowler's article presents the Richardson Maturity Model as a way to explain progression from RPC over HTTP, to resources, to HTTP verbs, to hypermedia controls. The article is useful as a teaching model, but it is not a formal standard.

For Flowsy DevGuide, the model should be used carefully:

- Level 0 helps identify RPC-style endpoints that ignore HTTP semantics.
- Level 1 encourages resources and collection/item structure.
- Level 2 introduces HTTP verbs and status codes as protocol semantics.
- Level 3 introduces hypermedia controls, which may be useful for discoverability and workflow navigation but should not be treated as mandatory for every internal or application API.

Source: https://martinfowler.com/articles/richardsonMaturityModel.html

### REST Constraints

Roy Fielding's REST architectural style chapter is the primary conceptual source for REST. It should be used to avoid overclaiming that any HTTP API with resource paths and status codes is fully RESTful.

The DevGuide should prefer precise language such as "HTTP API", "resource-oriented API", "REST-informed API" or "RESTful API" only when the documented constraints are intentionally met.

Source: https://ics.uci.edu/~fielding/pubs/dissertation/rest_arch_style.htm

### ASP.NET Core Minimal APIs

Current ASP.NET Core documentation for .NET 10 includes relevant guidance for:

- `AddProblemDetails()` and ASP.NET Core problem details services.
- Error handling middleware that can generate Problem Details responses.
- Minimal API response types, `TypedResults` and `Results<T1, TN>`.
- OpenAPI metadata produced by typed results.
- Authentication behavior for known API endpoints returning `401` and `403` instead of redirects in ASP.NET Core 10.

This matters because Flowsy examples are C# and Minimal API-oriented. The final guidance should show patterns that work naturally with typed results, endpoint metadata and integration tests.

Sources:

- https://learn.microsoft.com/en-us/aspnet/core/fundamentals/error-handling-api
- https://learn.microsoft.com/en-us/aspnet/core/fundamentals/minimal-apis/responses

### OpenAPI

OpenAPI 3.2.0 is the latest published OpenAPI Specification as of this analysis. It defines how responses, status codes, reusable response components, media types and links can be described.

This matters for documenting `application/problem+json` responses, reusable Problem Details schemas, known error responses and optional operation links without conflating OpenAPI links with Richardson Level 3 runtime hypermedia.

Source: https://spec.openapis.org/oas/latest

## Findings and Constraints

- The minimum useful API maturity baseline should likely be Richardson Level 2 for most HTTP APIs: resource-oriented URLs plus correct use of HTTP methods, status codes and content negotiation.
- Level 3 hypermedia should be treated as contextual rather than mandatory. It can be recommended for APIs where runtime discoverability, workflows or client navigation are explicit goals.
- Problem Details should be based on RFC 9457, not RFC 7807. If older platform or community docs mention RFC 7807, the guide should explain the replacement.
- The guide should distinguish HTTP status code semantics from application-specific problem types.
- Validation errors should use a Problem Details extension member rather than a custom top-level envelope that competes with RFC 9457.
- Traceability fields such as `traceId`, `correlationId` or `requestId` are useful extension candidates, but the guide must avoid promising support identifiers that are not actually searchable in logs.
- Examples must stay open source and community-oriented, using neutral domains such as orders, packages, projects, accounts, releases or subscriptions.
- Flowsy package references must use the expected naming: `Flowsy.Mediation`, `Flowsy.Db.Unity`, `Flowsy.*`, `flwdb`.
- Public package consumption should reference public registries such as NuGet or NPM where relevant; GitHub should remain source and contribution context.
- The final visible documentation change requires a `CHANGELOG.md` update and `npm run docs:build` validation.

## Alternatives Considered

### Add Everything to Backend Concepts

This would keep the guidance in one general backend page.

Pros:

- Simple navigation.
- Good fit for language-neutral API principles.

Cons:

- The page would become too dense.
- C# Minimal API implementation details would either be too shallow or mixed into general guidance.

### Add Only C# Minimal API Examples

This would focus on concrete code and avoid abstract API theory.

Pros:

- Immediately practical for Flowsy-style backend slices.
- Easy to validate with existing examples.

Cons:

- It would not provide enough conceptual grounding for API maturity.
- It could make HTTP and Problem Details choices look framework-specific when they are standards-driven.

### Create a Dedicated API Design Page Plus Targeted Updates

This would create a focused backend API design page and then update C# and AI-agent pages only where implementation details belong.

Pros:

- Separates durable HTTP principles from framework-specific examples.
- Gives agents and developers a clear source to read before modifying API contracts.
- Leaves room for future library, template or tool follow-up without implementing it prematurely.

Cons:

- Requires navigation updates and careful cross-linking.
- Needs editorial discipline to avoid duplicating content across backend pages.

## Proposed Approach

Use the dedicated page plus targeted updates approach.

The final documentation should:

- Add a new backend page for HTTP API design maturity and Problem Details.
- Update `technologies/backend/concepts.md` so it points to the new API design guidance instead of carrying all details.
- Update the C# Minimal API page with concise examples for `TypedResults`, `Results<T1, TN>`, `ProblemDetails` and representative status codes.
- Update the backend VSA context guide so agents consult official HTTP and Problem Details sources for API work.
- Update relevant testing guidance only if needed to cover integration checks for status code, content type and Problem Details shape.
- Update `CHANGELOG.md` once the visible guide content is implemented.

## Proposed Minimum Baseline

The proposed baseline for later implementation is:

- Model stable concepts as resources when they have identity, collection behavior or lifecycle.
- Use HTTP methods according to their semantics, especially safety and idempotency.
- Use status codes to communicate protocol-level outcomes before adding application-specific details.
- Represent common client and server errors with RFC 9457 Problem Details.
- Document successful and known error responses in OpenAPI.
- Keep hypermedia controls optional unless the API deliberately supports runtime navigation or workflow discovery.

## Risks and Open Questions

- The guide must avoid creating a checklist that implies Level 2 equals full REST compliance.
- Validation error shapes can diverge across platforms; the final guidance should pick one clear pattern while explaining how it maps to RFC 9457 extensions.
- ASP.NET Core has built-in Problem Details behavior, but real projects often customize errors through filters, middleware or result mappers. The examples should stay adaptable.
- OpenAPI 3.2.0 is current, but many tools may still target 3.0.x or 3.1.x. The guide should avoid relying on 3.2-only features unless they are clearly optional.
- Future Flowsy library or template work should be documented as follow-up, not bundled into the first documentation update.

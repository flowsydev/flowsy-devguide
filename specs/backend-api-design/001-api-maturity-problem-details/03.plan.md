# Plan - API Maturity and Problem Details Guidance

## General Strategy

Update Flowsy DevGuide in phases after this plan is reviewed and approved. Keep the first implementation focused on public documentation, not package or template changes.

The documentation should establish a practical HTTP API baseline: resource-oriented design and correct HTTP semantics as the minimum expectation, RFC 9457 Problem Details for standardized errors, and optional hypermedia guidance for APIs that need runtime discoverability.

> [!WARNING]
> Do not execute this plan until the developer has reviewed and approved it.

## Phase 1 - Confirm Content Inventory and Final Structure

- Re-read the current backend, C# conventions, Minimal API examples, testing and AI context guide pages.
- Confirm the final page location, with `technologies/backend/api-design.md` as the leading candidate.
- Decide which existing pages receive short cross-links versus concrete examples.
- Confirm whether the sidebar should expose the new page under `Technologies > Backend`.

## Phase 2 - Draft the API Design Guidance

- Create the new backend API design page.
- Explain the Richardson Maturity Model as a teaching model, not a standard.
- Recommend the practical baseline:
  - avoid RPC-style endpoints when a resource model fits;
  - model collections and items consistently;
  - use HTTP methods according to RFC 9110 semantics;
  - use status codes intentionally;
  - document known responses.
- Explain when Level 3 hypermedia is useful and when it can be deferred.
- Include neutral open source examples such as packages, orders, accounts, projects or releases.

## Phase 3 - Draft the Problem Details Guidance

- Add RFC 9457 Problem Details guidance to the new API design page or a tightly linked subsection.
- Document `application/problem+json`.
- Explain `type`, `title`, `status`, `detail`, `instance` and extension members.
- Define a recommended validation error extension shape.
- Define traceability guidance for `traceId`, `correlationId` or `requestId`.
- Include security and privacy rules for error details.
- Mention that RFC 9457 obsoletes RFC 7807.

## Phase 4 - Update Implementation-Oriented Pages

- Update `technologies/backend/concepts.md` with a concise pointer to the API design page.
- Update `technologies/backend/vertical-slice-architecture/csharp-minimal-apis.md` with representative Minimal API patterns:
  - `TypedResults`;
  - `Results<T1, TN>`;
  - success and error result types;
  - Problem Details responses;
  - response metadata for OpenAPI.
- Update `technologies/backend/dotnet/csharp.md` only if endpoint naming or DTO guidance needs a small adjustment.
- Avoid broad refactors of existing examples unless required for consistency.

## Phase 5 - Update Agent and Validation Guidance

- Update `ai-assisted-development/context-guides/backend-vsa-minimal-api.md` so API work includes the new API design page in minimum context.
- Update `ai-assisted-development/agent-routing.md` only if API contract work needs an explicit routing row.
- Update testing guidance only if there is a clear gap around validating HTTP status codes, content type or Problem Details payloads.

## Phase 6 - Navigation, Changelog and Build Validation

- Register the new page in `.vitepress/config.ts` if it should appear in navigation.
- Update `CHANGELOG.md` under the appropriate release heading.
- Run `npm run docs:build`.
- If build issues appear, fix only issues caused by this change.

## Validation Plan

- Documentation review:
  - headings use Title Case;
  - Flowsy naming remains consistent;
  - examples are general and community-friendly;
  - RFC 9457, RFC 9110, REST and Richardson model are represented with accurate status.
- Link review:
  - sidebar link resolves;
  - cross-links between backend concepts, Minimal APIs and context guides resolve;
  - external references point to official or stable sources.
- Build validation:
  - `npm run docs:build`.

## Expected Deliverables

- New or updated public DevGuide page for HTTP API maturity and Problem Details.
- Targeted updates to backend concepts, Minimal API examples and AI context guidance.
- `CHANGELOG.md` entry for the visible documentation change.
- Execution notes in `04.exec.phase-NN.md` files once the approved phases are run.
- Final summary in `05.summary.md` after implementation and validation.

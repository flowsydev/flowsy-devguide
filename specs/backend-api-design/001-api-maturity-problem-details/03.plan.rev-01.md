# Plan Review 01 - API Maturity and Problem Details Guidance

## Reason for Review

This review answers the open questions left by the analysis before asking for approval to execute the public documentation update. The goal is to reduce ambiguity around scope, page structure, maturity baseline, Problem Details shape and validation expectations.

## Plan Adjustments

The original plan remains valid. Execution should apply these clarifications:

- Phase 1 should confirm `technologies/backend/api-design.md` as the default target unless a conflicting structure is discovered during the final inventory.
- Phase 2 and Phase 3 should be implemented as one cohesive page, not as two disconnected documents.
- Phase 4 should keep Minimal API code examples short and focused on response shape, status codes and Problem Details integration.
- Phase 5 should update testing guidance only if the new API guidance introduces a concrete validation expectation not already covered by `technologies/testing/`.

## Open Questions and Decisions

### Where should the public API guidance live?

Decision: create a dedicated page at `technologies/backend/api-design.md`.

Reasoning: API maturity, HTTP semantics and Problem Details are backend technology guidance, but they are not specific to C#, Vertical Slice Architecture or a single implementation library. A dedicated backend page keeps the general standard-based content discoverable without overloading `technologies/backend/concepts.md`.

### Should the new page appear in navigation?

Decision: yes. Add it under `Technologies > Backend`, near `General Concepts` and before architecture-specific pages.

Reasoning: API contract design is a primary backend concern. If the page is not in the sidebar, agents and developers are more likely to miss it and continue relying on scattered references.

### What is the minimum API maturity baseline?

Decision: recommend Richardson Level 2 as the minimum practical baseline for most HTTP APIs.

The guide should phrase this as:

- Level 1 resource modeling is expected when the domain has identifiable resources, collections or lifecycles.
- Level 2 HTTP semantics are expected for methods, status codes and content negotiation.
- Level 3 hypermedia controls are contextual and optional, not a universal requirement.

Reasoning: Level 2 gives most projects a meaningful improvement over RPC-style HTTP without forcing hypermedia where it does not create enough value.

### How should the guide talk about REST?

Decision: use precise terms such as `HTTP API`, `resource-oriented API` and `REST-informed API` by default. Use `RESTful` only when the page is explicitly discussing REST constraints or a design that intentionally adopts them.

Reasoning: Richardson Level 2 is not full REST compliance. The guide should avoid teaching a shortcut that turns a maturity model into a certification claim.

### What status-code guidance should be included first?

Decision: include a compact decision table for common outcomes:

- `200 OK` for successful retrieval or processing with a response body.
- `201 Created` when a new resource is created and can be identified.
- `202 Accepted` for asynchronous or long-running processing accepted but not completed.
- `204 No Content` for successful operations with no response body.
- `400 Bad Request` for malformed or structurally invalid requests.
- `401 Unauthorized` for missing or invalid authentication.
- `403 Forbidden` for authenticated callers without permission.
- `404 Not Found` when the target resource is absent or intentionally hidden.
- `409 Conflict` for state conflicts such as duplicate, stale or incompatible operations.
- `422 Unprocessable Content` for syntactically valid requests that fail semantic validation when the API chooses to distinguish this from `400`.
- `500 Internal Server Error` for unexpected server failures with sanitized Problem Details.

Reasoning: This covers the common cases without pretending to replace RFC 9110.

### What Problem Details validation shape should be recommended?

Decision: recommend RFC 9457 core members plus a top-level `code` extension for the application problem category and an `errors` extension array for structured validation errors.

Each validation item should include, when available:

- `detail`: human-readable validation message.
- `pointer`: JSON Pointer to the invalid request member.
- `code`: stable validation code for that invalid member when clients need machine-readable branching.

Reasoning: RFC 9457 allows extension members. A top-level `code` lets clients branch on the overall application problem without parsing `detail`, while item-level codes remain available for field-specific validation behavior. RFC 9457 includes a validation example using an `errors` extension with `detail` and `pointer`.

### Which traceability extension should be preferred?

Decision: recommend `traceId` as the minimum extension when it maps to platform diagnostics, and allow `correlationId` or `requestId` only when the project actually logs and propagates them.

Reasoning: Traceability fields are useful only if support teams can search them. The guide should not encourage decorative identifiers.

### Should the guide rely on OpenAPI 3.2.0 features?

Decision: use OpenAPI generally for documenting successful and known error responses, but avoid requiring 3.2-only features in initial examples.

Reasoning: OpenAPI 3.2.0 is current, but many tools still lag behind. The guide can cite the latest spec while keeping examples compatible with common OpenAPI 3.x usage.

### Should implementation add reusable package or template support?

Decision: no. Keep package, template and CLI improvements as deferred follow-up.

Reasoning: The current spec is about preparing and updating the DevGuide. Implementation libraries should be planned separately after the documentation baseline is accepted.

### Which examples should Flowsy use?

Decision: use general community and open source domains: packages, orders, projects, accounts, releases, subscriptions or repository resources.

Reasoning: Flowsy DevGuide targets an open source audience. Examples should stay broadly applicable and avoid organization-specific language.

### What validation is required after execution?

Decision: run `npm run docs:build` after documentation changes. During review, also check links, sidebar placement, source citations and whether examples fit the selected audience.

Reasoning: These are documentation changes in a VitePress site, so build validation and link/navigation review are the relevant minimum checks.

# Plan Review 02 - Top-Level Problem Details Error Code

## Reason for Review

After implementation, the developer identified that the recommended Problem Details structure would benefit from a top-level `code` extension. This helps clients make application-level decisions without parsing `detail`, even when the response does not include a validation `errors` collection.

## Adjustment

Add a stable top-level `code` extension to the Problem Details guidance and examples.

## Decision

Use both HTTP `status` and application `code`:

- `status` communicates the protocol-level outcome.
- `code` communicates the stable application problem category.

For validation responses:

- the top-level `code` identifies the overall problem, such as `validation.failed`;
- item-level `code` values identify specific invalid member rules only when clients need them.

## Rationale

RFC 9457 permits extension members. A documented top-level `code` is useful for clients that need deterministic behavior without coupling to localized or human-readable `detail` text.

## Impact

- Update `technologies/backend/api-design.md`.
- Update the Minimal API `ProblemDetails` example.
- Update execution notes and summary.
- Keep the change inside documentation; do not add package or template support in this spec.

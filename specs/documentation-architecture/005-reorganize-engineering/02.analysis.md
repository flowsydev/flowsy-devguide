# 005 — Analysis

## Problem

Under Technologies, Data and Messaging nest under Backend, hiding independent audiences. After promoting Testing to Quality, Technologies can become Engineering without dragging Quality along. Dependency safety still sits with repository documentation.

## Evidence

- Data and messaging readers should not start at backend concepts.
- Kafka/Redpanda event-store intent must remain distinct even when messaging also references Kafka.
- Thin Cross-Cutting landings can exist before full consolidation in 007.
- `flwdb` belongs with Data migrations tooling, not Backend narrative pages.

## Options Considered

| Option | Pros | Cons |
| --- | --- | --- |
| Engineering with sub-areas | Matches reader intent | Large move surface |
| Keep Technologies label | Less rename churn | Misnames the area |
| Nest Data under Backend forever | Familiar to backend authors | Hides data audience |

## Decision

Create `content/engineering/` with Backend, Data, Messaging, Frontend, Security and Cross-Cutting. Bridge previous `/technologies/**` routes. Leave long-page splits and full topic consolidation to later work lines.

## Risks

- Leftover `/technologies/` links in context guides and references.
- Background Services must stay under .NET while linking Messaging for Outbox/Kafka behavior.
